# แผนสำรวจและปรับ UX/UI ทั้งระบบ

วันที่สำรวจ: 12 กันยายน 2026

## สถานะและขอบเขตหลักฐาน

เฟส 1: สำรวจ route และโครงสร้างโค้ดเบื้องต้นแล้ว พบ 22 page entrypoints รวม redirect `/admin` และหน้าเอกสารพิมพ์ โดย dynamic routes ครอบคลุมหลายระเบียนและหลายชนิดฟอร์ม จึงไม่ใช่จำนวนหน้าจอหรือสถานะทั้งหมด

ยังไม่ได้ตรวจภาพในเบราว์เซอร์หรือทดสอบขั้นตอนจริงทุกหน้า ผลจากการค้นหาโค้ดเป็นรายการตรวจต่อ ไม่ใช่คำยืนยันว่าหน้านั้นมีปัญหาทั้งหมด ไม่ประเมินความสมบูรณ์เป็นเปอร์เซ็นต์จนมีเกณฑ์ตรวจและผลจริง

เอกสารเริ่มจากการสำรวจ ต่อมาผู้ใช้สั่งดำเนินการปรับปรุงแล้ว

## ความคืบหน้า implementation — 12 กันยายน 2026

แก้จากหลักฐานโค้ดแล้ว แต่ยังไม่ถือว่าตรวจรับ UX/UI ทั้งระบบเสร็จ:

- เอกสาร: สิทธิ์ IT-only, PDF count/filter, action bar, สีคงที่, loading ตรงโครงค้นหา/กริด/ตาราง
- สรุปคำร้อง: ขนาดข้อความ สีรอง label และชื่อไฟล์ยาว
- รายละเอียด/ยืมคืน: loading 5 ช่อง, ขั้นตอนตัดบรรทัด, select ไม่บังคับ 240px, ตรวจ selection กับ availability ล่าสุด, ปิด dialog เมื่อรับคืนสำเร็จ
- ประเมิน: ลูกศรวน 1–5 และ Home/End เลือกคะแนนได้แม้ยังไม่เลือก, ปรับข้อความรอง
- Dashboard/รายการ/Excel: บริษัทคำร้องใช้ serviceSiteCode; ลิงก์ฟอร์มใช้ทุกสถานะและช่วงสร้าง; ยอดปิดส่งช่วงปิด; รายการและ export ใช้ cutoff เดียวกัน; pagination ตรวจจำนวนเต็ม
- ยืมคืน: overdue dashboard ใช้บริษัทอุปกรณ์เหมือนหน้ารายการยืมคืน
- ทะเบียน: focus ช่องผิดเฉพาะหลัง submit ไม่กระโดดระหว่างพิมพ์, รองรับ error body อ่านไม่ได้, ไม่ส่งไป /assets/undefined, สีช่องกรอกและข้อความช่วย
- แก้ไข/พิมพ์: ตรวจ route guards/ค่าเริ่มต้น/ทางกลับ; แก้ข้อความสิทธิ์ IT ให้ตรงกรณียกเลิก
- ผู้ดูแล: ตรวจโค้ด busy/error/confirmation ของ users, approvers, holidays เบื้องต้น มีรองรับอยู่แล้ว ยังไม่ทดสอบ mutation จริง
- หน้าแรก: จำกัดความกว้าง skeleton ที่เสี่ยงล้น คงภาพและ animation

การตรวจ: TypeScript และ ESLint ตามไฟล์ที่แก้; ตรวจ cutoff ด้วยค่าปกติ/เขตเวลา/ค่าว่าง/ค่าผิดรูปแบบ ไม่รัน full build หรือแก้ DB เพื่อทดสอบ

ยังต้องตรวจรับ: ภาพที่ 390/768/1366/1920px, keyboard, workflow ทุกบทบาท/ทุก F-code, success/error, จำนวน dashboard เทียบ DB, PDF/การแบ่งหน้าพิมพ์ และการบันทึกหน้าผู้ดูแล

ข้อจำกัด: session นี้ไม่มีเครื่องมือ browser และไม่มี Playwright ในโปรเจกต์ จึงยังไม่มีหลักฐาน visual หรือ end-to-end ห้ามตีความ static checks ว่าหน้าจอจริงผ่านแล้ว หน้า knowledge ยังเป็น placeholder; ทีม IT ต้องจัดหา/ยืนยันคู่มือและ FAQ ก่อนเผยแพร่

## สิ่งที่ต้องรักษา

- รักษาสีและฟอนต์ปัจจุบันระหว่างสำรวจ: brand #175cd3, sidebar #1c2f52, IBM Plex Sans Thai จาก globals.css และ app/layout.tsx ค่านี้เป็น baseline ปัจจุบัน ไม่ใช่การยืนยันว่าเป็นสีเดิมที่ผู้ใช้ชอบทั้งหมด
- รักษา public/TSM.png, public/Home.png และภาพ/อนิเมชันเดิมจนมีคำขอแก้เฉพาะส่วน
- ใช้ภาพอ้างอิงที่ผู้ใช้เลือกกับหน้าเอกสารเป็นต้นแบบเฉพาะหน้านั้น ไม่บังคับทุกหน้าให้เป็นกริดหรือแบนเนอร์เหมือนกัน
- ห้ามปรับ shared layout หรือ tokens เพื่อแก้ปัญหาเฉพาะหน้าโดยไม่ตรวจผลกระทบหน้าอื่น
- ก่อนแต่ละกลุ่ม: ปัญหา → ภาพ/ข้อเสนอที่เห็นผลชัด → ขอบเขตไฟล์ → ลงมือ → ตรวจรับ
- AGENTS.md ยังกล่าวถึง Kanit/Itim และ 5 ฟอร์ม แต่โค้ดปัจจุบันใช้ IBM Plex Sans Thai และ 8 ฟอร์ม ส่วน ui-foundation.md บางข้อไม่ตรงโค้ดปัจจุบัน จึงต้องทบทวนตามคำสั่งล่าสุดของผู้ใช้ ไม่ย้อน UI ตามเอกสารเก่าอัตโนมัติ

## แผนดำเนินงาน

### เฟส 1 — สำรวจเชิงลึกและกำหนด baseline

สถานะ: บัญชี route และ structural audit เสร็จเบื้องต้น; visual/interaction audit ยังไม่ครบ

ตรวจตัวแทนแต่ละกลุ่มพร้อมหน้าใกล้เคียง บันทึกปัญหาที่ทำซ้ำได้ เส้นทาง/บทบาท/ขนาดจอ/ผลที่คาดหวังและผลจริง ถ้าใช้เบราว์เซอร์ให้เป็นรอบที่ผู้ใช้ร้องขอ

### เฟส 2 — ภาพต้นแบบและแนวทางส่วนร่วม

ทำภาพตัวแทน 4 ประเภท: รายการ, แบบฟอร์ม, รายละเอียดพร้อมปุ่มทำงาน, dashboard โดยรักษา baseline ที่ตกลงไว้ กำหนดขนาดข้อความ ระยะห่าง ปุ่มและสถานะจากตัวอย่างที่เลือก แล้วค่อยปรับเอกสาร foundation ให้ตรง ห้ามถือว่าโครงเดียวใช้ได้กับทุกหน้า

### เฟส 3 — เส้นทางคำร้อง (ลำดับแรกของ implementation)

เริ่มจากเอกสาร/เลือกบริการ → สร้างคำร้องทุก F-code → รายละเอียด → แก้ไข → ประเมิน/พิมพ์ แก้ P1 ก่อน เน้นสิทธิ์ ทางเข้าที่ชัด ข้อมูลที่จำเป็น validation การป้องกันกดส่งซ้ำ และสถานะหลังส่ง แยกตรวจ F02 IT-only, F03 ยืม, F07/F10 อนุมัติ และ F13 ฟิลด์เฉพาะ

### เฟส 4 — งานเจ้าหน้าที่และข้อมูลอุปกรณ์

รายการคำร้อง + dashboard ร่วมกัน: ตัวกรองและขอบเขตตัวเลข/ลิงก์ต้องสอดคล้องกัน

assets list/new/detail/edit ร่วมกัน: field labels, การจัดหมวด, ข้อมูลว่าง, บันทึก

loans + loan-items + LoanPanel ร่วมกัน: วันครบกำหนด สถานะอุปกรณ์ การคืนและต่ออายุ

### เฟส 5 — หน้ารองและผู้ดูแล

users/approvers/holidays: การบันทึกและข้อความผลลัพธ์ที่ตรงกันตามสิทธิ์

login/home: ปรับเฉพาะปัญหาที่สำรวจพบ รักษาภาพและ animation เดิม

knowledge: ระบุเนื้อหาที่ต้องมีและผู้รับผิดชอบจัดหา ไม่แต่งคู่มือหรืออ้างว่ามีเนื้อหาจริง

### เฟส 6 — ตรวจรับข้ามระบบ

- ขนาดจอ 390, 768, 1366 และ 1920px; หน้าไม่ล้นแนวนอนโดยไม่จำเป็น ตารางที่ต้องเลื่อนมีทางเข้าปุ่มสำคัญชัด
- keyboard: ลำดับ Tab, focus, Enter, Escape และคืน focus หลังปิด dialog
- บทบาทผู้ใช้ทั่วไป/IT/ผู้อนุมัติ/admin ตามสิทธิ์จริงและข้อมูลทดสอบ
- สถานะ: loading, empty, ไม่มีผลค้นหา, error, pending, success, access denied
- คำร้อง: เปิด, รับงาน, ดำเนินการ, รอยืนยัน, ปิด, ยกเลิก และสถานะอนุมัติที่ใช้จริง
- ข้อมูลยาว: ชื่อบุคคล/หน่วยงาน/ไฟล์, ไม่มี assignee, attachments หลายไฟล์
- ปุ่มอันตรายต้องมี confirmation; การทดสอบที่เปลี่ยนข้อมูลใช้ชุดทดสอบที่อนุญาต ไม่ส่งเมลหรือคำร้องจริงเพื่อ audit
- ใช้ typecheck/lint ตามขอบเขตการแก้; ไม่รัน full build โดยไม่จำเป็นตาม AGENTS.md

## เกณฑ์จบแต่ละกลุ่ม

1. มีรายการปัญหาและขอบเขตไฟล์ก่อนแก้
2. ภาพ/โครงที่เลือกสะท้อนความต้องการล่าสุดของผู้ใช้
3. งานหลักทำได้ครบและไม่มีทางเข้าที่ดูใช้ได้แต่ทำไม่ได้
4. ผ่านการตรวจจอเล็ก/ใหญ่และสถานะที่เกี่ยวข้อง หรือระบุชัดว่าส่วนใดยังไม่ได้ตรวจ
5. สรุปสิ่งที่เปลี่ยน หลักฐานตรวจ และสิ่งค้าง ก่อนเริ่มกลุ่มถัดไป

- ไม่พบ document-level horizontal overflow ในหน้าที่ตรวจ ตาราง desktop ที่กว้างถูกแทนด้วยรายการ mobile หรืออยู่ในพื้นที่เลื่อนเฉพาะส่วนตามการออกแบบ
- พบ dashboard ล้มหลังเพิ่มคะแนนประเมิน 3 มิติ เพราะ dev server ยัง cache Prisma Client รุ่นเก่า แก้โดยตรวจ migration และรีสตาร์ต server; ตรวจซ้ำแล้วหน้า dashboard แสดงผลได้ทุกขนาดที่กำหนด
- ปรับ KPI dashboard บนมือถือเป็น 2 คอลัมน์เพื่อลดความยาวหน้า และตั้งโลโก้เหนือ fold ให้โหลดแบบ eager ตาม Next.js 16
- ตรวจ `npm run check` ผ่าน: ESLint, TypeScript และ ticket date cutoff test
- ยังไม่ทดสอบ mutation จริงทุกกรณี เช่น สร้างคำร้อง, อนุมัติ, ให้ยืม/คืน, แก้สิทธิ์ และส่งแบบประเมิน เพราะการตรวจรอบนี้หลีกเลี่ยงการเปลี่ยนข้อมูล demo โดยไม่จำเป็น
